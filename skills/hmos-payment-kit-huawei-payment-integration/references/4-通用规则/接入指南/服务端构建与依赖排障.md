# 服务端构建与依赖排障

> 适用于 Java / Spring Boot 服务端在接入华为支付、签名验签或证书读取时，出现 Maven 依赖、插件解析、`程序包不存在`、证书链或 PEM 解析相关问题的场景。

## 使用时机

- 用户在服务端工程中新增了支付 SDK、签名库、证书库或 HTTP 客户端扩展。
- 报错包含 `package xxx does not exist`、`程序包xxx不存在`、`PluginResolutionException`、`DependencyResolutionException`、`PKIX path building failed`。
- 工程是 starter、样例工程或最小闭环，目标优先是“可编译、可启动、可替换”。

## 最小判断顺序

1. 先判断是“依赖没拉下来”还是“代码 import 写错了”。
2. 再判断是“官方 SDK 不可验证”还是“普通辅助依赖不可解析”。
3. 最后才判断支付字段、签名逻辑或回调逻辑本身。

不要在依赖解析失败时，直接把问题归因为 Payment Kit 字段错误或接口逻辑错误。

## Maven / Gradle 依赖新增规则

- 只要准备新增 Maven / Gradle 依赖，先验证依赖是否可解析，再写依赖相关 `import` 和实现。
- 若依赖未验证成功，不要先提交带未解析 `import` 的源码。
- 对 starter / 样例工程，优先保证“源码可编译、结构可替换、配置可注入”，不要先追求最完整实现。

## PEM / 证书处理默认策略

- 若只是处理 PEM 私钥、公钥或证书读取，优先采用“纯 JDK + 最小必要依赖”的实现。
- 不要默认引入 `bcpkix` 的 `PEMParser`、`JcaPEMKeyConverter` 等类。
- 只有在明确需要复杂 PEM 结构解析，且依赖已验证可下载时，才引入更重的证书解析依赖。

## 常见报错分流

### 1. `package xxx does not exist` / `程序包xxx不存在`

优先排查：

1. 该包对应依赖是否真的已经解析成功。
2. `pom.xml` / `build.gradle` 是否已经声明了依赖。
3. 当前源码里是否提前写入了依赖相关 `import`。
4. IDE 缓存是否滞后于构建结果。

不要第一时间把这类错误判断成“支付签名算法不对”。

### 2. `PKIX path building failed`

优先判断为：

- 企业镜像证书链问题
- 插件仓 / 依赖仓 HTTPS 证书问题
- 本地 JDK truststore 或公司内网代理问题

不要误判为：

- Payment Kit 接口字段错误
- 回调验签逻辑错误
- 华为支付官方 SDK API 不存在

### 3. `PluginResolutionException` / `DependencyResolutionException`

优先判断为：

- Maven 插件仓或依赖仓不可达
- 企业镜像配置异常
- 本地缓存损坏或被失败结果缓存

先验证构建环境，再继续改支付代码。

## 官方 SDK 不可验证时的处理

- 保留“SDK 适配层 + HTTP 网关兜底”的结构。
- 不得伪造 SDK 类名、配置对象、方法签名或请求/响应对象。
- 可以先保留接口层、配置层和实现占位，但要明确标注“当前为降级方案”。

## starter / 样例工程优先级

对 starter、最小闭环或样例工程，优先级按下面顺序执行：

1. 可编译
2. 可启动
3. 可配置
4. 可替换
5. 再考虑完整支付闭环能力

如果完整实现和可编译之间冲突，优先保住可编译。
